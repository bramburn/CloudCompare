# Migration Strategy — Incremental C++ → Rust for CloudCompare
**Date:** 2026-08-19
**Source:** Perplexity AI + codebase analysis

---

## 1. The Fundamental Principle: Incremental, Not Rewriter

Every major successful C++ → Rust migration at scale has used **incremental replacement**, not a big-bang rewrite. The canonical examples:

| Company | Approach | Outcome |
|---------|----------|---------|
| **Discord** | Rust in hot paths (Readja, voice processing) | 10× throughput improvement; C++ replaced incrementally |
| **Dropbox** | Rust for storage engine (Perfcheck client) | Eliminated entire bug classes; gradual adoption |
| **Cloudflare** | workerd edge runtime — Rust + C++ (via workerd-cxx fork) | Production edge; zero downtime migration |
| **Google** | Crubit project — bidirectional C++/Rust interop | Ongoing; Android codebase integration |
| **Meta** | Rust in source control, build tools, proc-macro libs | Fi's compiler, Mononoke SCM backend |
| **ClickHouse** | 98% C++ with Rust modules since 2021 | Active; Rust covers new hot paths |

**The pattern is universal:** Start at the edges, establish FFI, ship incrementally, measure, expand.

---

## 2. Why Not a Full Rewrite for CloudCompare

CloudCompare is a poor candidate for a full rewrite because:

1. **GPL licensing**: The fork's obligations mean any rewrite must preserve GPL compatibility
2. **Qt6 GUI dependency**: ~50k lines of Qt-dependent UI code cannot be meaningfully rewritten without rewriting the entire Qt layer
3. **Active plugin ecosystem**: 16 enabled plugins, each with their own build and ABI surface
4. **User-facing stability**: A rewrite would break every user's workflow, plugin, and script
5. **No team of Rust engineers**: The developer (Icelabz/bramburn) is working alone on this codebase

**The realistic model:** Keep the Qt/GUI layer in C++. Migrate the compute kernels (CCCoreLib) to Rust progressively. The result is a hybrid C++/Rust binary.

## 3. Migration Sequencing Principles

### 3.1 The Beachhead Rule

**Start with the smallest, most isolated, highest-value component** — not the most critical or most broken.

A good beachhead has:
- Minimal dependencies on the rest of the codebase
- A well-defined input/output contract
- No Qt / GUI / OpenGL dependencies
- An existing test suite or characterisation test target
- Low risk of failure affecting users

### 3.2 The Three Integration Problems

Before writing meaningful Rust, solve:

1. **Build integration**: How does Rust fit into `cmake` / `ninja`? → Use `cxx-build` + CMake `FetchContent` or a custom target that calls `cargo`
2. **FFI ownership**: Who allocates? Who frees? Who can mutate? → Design the boundary first
3. **Testing continuity**: Do ASAN/MSAN/TSAN still run across the boundary? → Add `cargo test` to the CMake test target

## 4. FFI Boundary Design — The Five Questions

Every value crossing the C++/Rust boundary must be documented:

```
┌─────────────────────────────────────────────────────────────┐
│ Q1: WHO OWNS this value?                                    │
│   • C++ owns → pass by reference or pointer                 │
│   • Rust owns → pass Box<T> across FFI                     │
│   • Shared → Arc<RwLock<T>> or explicit Copy               │
│                                                              │
│ Q2: WHO CAN MUTATE it?                                      │
│   • Exclusive → &mut T (C++ equivalent: T&)                │
│   • Shared read → &T (C++ equivalent: const T&)             │
│   • Thread-safe → Arc<RwLock<T>>                           │
│                                                              │
│ Q3: HOW LONG IS IT VALID?                                    │
│   • Lifetime of a function call → safe to borrow            │
│   • Outlives the call → Rust must heap-allocate (Box)        │
│   • C++ must not use it after Rust drops it                 │
│                                                              │
│ Q4: CAN IT ALIAS?                                           │
│   • No aliased mutation in Rust → design prohibits it        │
│   • Two references to the same data → Arc<RwLock>           │
│                                                              │
│ Q5: WHO FREES IT?                                           │
│   • Rust heap-allocated → Drop called automatically          │
│   • C++ heap-allocated → CXX conversion to Rust uses clone  │
│   • No manual delete in Rust code                           │
└─────────────────────────────────────────────────────────────┘
```

## 5. CXX FFI — Specific Patterns for CloudCompare

### 5.1 Pass a Point Cloud View to Rust

```cpp
// C++ side — calling Rust to compute RMS
#include "cc_rust.hpp"  // generated by CXX

void ComputeRMSOnRust(GenericCloud* lCloud, GenericCloud* rCloud,
                      const ScaledTransformation& trans) {
    // Wrap C++ clouds as CXX opaque types
    auto l_view = rust::Box<RustCloudView>::default(
        RustCloudView::from_cloud(lCloud));  // copies point data
    auto r_view = rust::Box<RustCloudView>::default(
        RustCloudView::from_cloud(rCloud));

    // Call Rust — CXX handles conversion
    double rms = rust_compute_rms(*l_view, *r_view, trans);

    // Rust ownership transferred; C++ retains original clouds
}
```

```rust
// Rust side — src/lib.rs
#[cxx::bridge]
mod ffi {
    extern "Rust" {
        type RustCloudView;
        fn from_cloud(cloud: &CxxCloudData) -> Box<RustCloudView>;
        fn rust_compute_rms(l: &RustCloudView, r: &RustCloudView,
                           trans: &ScaledTransformation) -> f64;
    }

    extern "C++" {
        include!("CCCoreTypes.h");
        type CxxCloudData;  // wraps GenericCloud*
    }
}

pub struct RustCloudView {
    points: Vec<[f32; 3]>,
    normals: Option<Vec<[f32; 3]>>,
    scalar_field: Option<Vec<f32>>,
}

impl RustCloudView {
    pub fn from_cloud(cloud: &CxxCloudData) -> Box<Self> {
        let n = cloud.size() as usize;
        let mut points = Vec::with_capacity(n);
        for i in 0..n {
            let p = cloud.getPoint(i);
            points.push([p.x, p.y, p.z]);
        }
        Box::new(RustCloudView { points, normals: None, scalar_field: None })
    }

    pub fn rust_compute_rms(&self, other: &RustCloudView,
                            trans: &ScaledTransformation) -> f64 {
        let mut sum_sq = 0.0;
        let n = self.points.len().min(other.points.len());
        for i in 0..n {
            let transformed = transform_point(&self.points[i], trans);
            let diff = [
                transformed[0] - other.points[i][0],
                transformed[1] - other.points[i][1],
                transformed[2] - other.points[i][2],
            ];
            sum_sq += diff[0]*diff[0] + diff[1]*diff[1] + diff[2]*diff[2];
        }
        (sum_sq / n as f64).sqrt()
    }
}
```

### 5.2 Threading Across the FFI Boundary

```cpp
// C++ side — TBB parallel for calling Rust octree cell function
// In DgmOctree.cpp, replace:
tbb::parallel_for(tbb::blocked_range<std::size_t>(0, cells.size()),
[&](tbb::blocked_range<std::size_t> r) {
    m_MT_wrapper.launchOctreeCellFunc(cells[i]);  // ← C++ implementation
});

// With:
tbb::parallel_for(tbb::blocked_range<std::size_t>(0, cells.size()),
[&](tbb::blocked_range<std::size_t> r) {
    for (auto i = r.begin(); i < r.end(); ++i) {
        rust_launch_octree_cell(&cells[i], &m_MT_wrapper);  // ← CXX bridge
    }
});
```

```rust
// Rust side — rayon for thread-safe parallelism
#[no_mangle]
extern "C" fn rust_launch_octree_cell(
    desc: *const OctreeCellDesc,
    wrapper: *mut MTWrapper,
) -> bool {
    // SAFETY: C++ side guarantees desc is valid for the duration of this call
    // SAFETY: wrapper is protected by C++ mutex (initial approach)
    let desc = unsafe { &*desc };
    let wrapper = unsafe { &mut *wrapper };

    let result = std::panic::catch_unwind(|| {
        // Use rayon for fine-grained Rust parallelism
        // OR call back into C++ TBB — not both at once
        compute_cell_sequential(desc, wrapper)
    });

    match result {
        Ok(r) => r,
        Err(_) => {
            wrapper.cell_func_success = false;  // atomic write
            false
        }
    }
}
```

## 6. Build System Integration (CMake + Cargo)

### 6.1 Recommended CMake Snippet

```cmake
# In tools/cc-configure.cmd or CCCoreLib/CMakeLists.txt:

# --- Rust setup ---
find_package(Rust QUIET)
if(NOT Rust_FOUND)
    message(WARNING "Rust not found. Set RUST_HOME or install via rustup.")
endif()

# FetchContent for CXX (or add to vcpkg if available)
include(FetchContent)
FetchContent_Declare(cxx
    GIT_REPOSITORY https://github.com/dtolnay/cxx.git
    GIT_TAG v1.0.186
    GIT_SHALLOW TRUE
)
FetchContent_MakeAvailable(cxx)

# --- cc-rust library ---
add_custom_target(cc_rust_lib ALL
    COMMAND ${CMAKE_COMMAND} -E env
        CARGO_TARGET_DIR=${CMAKE_BINARY_DIR}/cc_rust
        $<TARGET_FILE:rfc>cargo build
            --manifest-path ${CMAKE_SOURCE_DIR}/cc-rust/Cargo.toml
            --release
            --target-dir ${CMAKE_BINARY_DIR}/cc_rust
    WORKING_DIRECTORY ${CMAKE_SOURCE_DIR}/cc-rust
    COMMENT "Building cc-rust library"
    VERBATIM
)
add_dependencies(CCCoreLib cc_rust_lib)

# Link into CCCoreLib
target_link_libraries(CCCoreLib PRIVATE
    ${CMAKE_BINARY_DIR}/cc_rust/release/libcc_rust.a
    cxx-build  # CXX codegen dependency
)
```

## 7. Characterization Testing Before Migration

Before touching any module, write characterization tests:

```cpp
// In qCC/test/TestScalarField.cpp — add Rust comparison test
void TestScalarField::testRustParity() {
    // Given: a scalar field with known values
    ccPointCloud cloud;
    cloud.reserve(1000);
    for (int i = 0; i < 1000; ++i)
        cloud.addPoint(CCVector3(i, i*2, i*3));

    auto* sf = cloud.theScalarFields()->getAt(0);
    double cpp_mean = ScalarFieldTools::ComputeMeanDistance(&cloud, 0, 1);
    
    // Call Rust implementation (same algorithm)
    double rust_mean = rust_compute_mean(sf->data(), sf->size());
    
    // Assertions — must be bit-identical (for f32)
    QVERIFY(qAbs(cpp_mean - rust_mean) < 1e-6);
}
```

**Key rule:** Run the characterization test in CI **before** the Rust migration to establish the baseline. After migration, the Rust version must pass the same test.
